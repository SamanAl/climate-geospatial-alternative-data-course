# Data dictionary and provenance

## Case data — entirely synthetic

Generated by `scripts/build_data.py` with NumPy's random seed 42. The code is the full recipe. Geometry uses real-world longitude/latitude near Houston, but every asset, service area, corridor and climate value is fictional. Do not overlay these values in a report about actual Houston climate or properties.

| File | Meaning | Units / CRS | Deliberate teaching feature |
|---|---|---|---|
| `assets.csv` | 12 fictional asset records | Coordinates in degrees, EPSG:4326 | A11 lies outside area and raster coverage |
| `assets.geojson` | Same records as point features | WGS84 longitude, latitude | Easy-to-read geometry and attributes |
| `assets.gpkg` | Same point records, layer `assets` | EPSG:4326 | Single-file geospatial container |
| `shapefile_example/assets.*` | Points with asset ID and sector only | EPSG:4326 | Multiple companion files; subset of attributes |
| `service_areas.geojson` | Two adjacent fictional rectangles | EPSG:4326 | Shared boundary at longitude −95.35 |
| `corridor.geojson` | One fictional line | EPSG:4326 | Straight-line proximity, not a road network |
| `synthetic_daily_temperature.nc` | 1991–2024 daily maximum temperature; 6 × 6 cells | Kelvin; geographic grid | Seasonality, imposed trend and missing cells |
| `synthetic_hot_days_2024.tif` | Derived count of 2024 daily maxima ≥35°C | Days; EPSG:4326; 0.05° cells | Nodata = −9999; A12 samples nodata |

### Asset fields

- `asset_id`: unique, fictional key. Keep it for joins.
- `asset_name`: fictional name, not a geocodable property address.
- `sector`: classroom grouping.
- `longitude`, `latitude`: decimal degrees. Geometry construction uses longitude first.
- `equity_usd_m`: invented equity capital in millions of USD; neither property value nor loss.
- `cooling_backup_verified`: boolean. False means backup has not been verified for the case; it does not prove there is no backup. This is an illustrative diligence attribute, not an engineering assessment.

### Climate recipe and missingness

At each grid cell, daily maximum Celsius temperature is 27 + a 9°C seasonal cosine peaking around day 205 + an imposed 0.045°C/year trend since 1991 + a spatial offset (−1.5 to 2.5°C) + shared daily noise + cell noise. Then 273.15 is added to store kelvin.

The entire northwestern grid cell is missing in every year. A second cell (row 1, column 1, zero-based) has all of 2005 missing. The GeoTIFF covers longitude −95.50 to −95.20 and latitude 29.60 to 29.90. Latitude coordinates descend from north to south; they are cell centers, not edges. This is a coarse illustrative grid, not site measurements.

Hot-day counts require at least 90% valid daily values within the calendar year. This completeness threshold is a teaching choice. For accepted incomplete years, counts are for available observations and are not adjusted to full-year totals. No missing values are imputed. The 2024 valid cells have complete daily coverage.

The 1991–2020 baseline and 2020–2024 recent comparison overlap in 2020. This is explicitly disclosed in Notebook 04; a stretch exercise removes the overlap. A five-year mean is not a 30-year normal.

## Real satellite example

`real_satellite_example.tif` is copied without changes from the existing local Planet tutorial file:

`E:\notebooks-master\jupyter-notebooks\getting-to-know-sat-imagery\example.tif`

The original repository is described at [planetlabs/notebooks](https://github.com/planetlabs/notebooks). The accompanying repository license is retained as `PLANET_REPOSITORY_LICENSE`. This records the repository provenance; it is not an independent audit of the image's acquisition metadata or any separate data terms.

The notebook inspects file structure and renders the first band. We do not establish its acquisition date, band calibration or suitability for climate analysis, and do not derive NDVI or temperature from it. Pixel percentiles are used only for a readable preview.

## References used to develop the lessons

Checked 15 September 2026. These explain concepts and formats; none supplied the synthetic climate values.

- [IETF GeoJSON specification](https://www.rfc-editor.org/rfc/rfc7946): geometry and coordinate order.
- [OGC GeoPackage](https://www.ogc.org/standards/geopackage/): geospatial database container.
- [OGC GeoTIFF](https://www.ogc.org/standards/geotiff/): raster georeferencing.
- [Unidata NetCDF guide](https://docs.unidata.ucar.edu/nug/current/): named multidimensional scientific data.
- [GeoPandas projections](https://geopandas.org/en/stable/docs/user_guide/projections.html): CRS labelling versus coordinate transformation.
- [Rasterio masks](https://rasterio.readthedocs.io/en/stable/topics/masks.html): missing raster values.
- [xarray time-series guide](https://docs.xarray.dev/en/stable/user-guide/time-series.html): time selection and aggregation.
- [Copernicus ERA5 explainer](https://climate.copernicus.eu/what-copernicus-climate-change-services-era5-reanalysis-dataset): reanalysis as a reconstruction of past conditions.
- [IPCC concept of risk](https://www.ipcc.ch/site/assets/uploads/2021/01/The-concept-of-risk-in-the-IPCC-Sixth-Assessment-Report.pdf): hazard, exposure and vulnerability.

## Moving to real data after this class

Choose a question and time period first. For a real temperature history, inspect a product such as ERA5 and its metadata before downloading a small subset. For real assets, obtain verified locations and appropriate permissions. Align coordinates, units, dates and spatial support; document data coverage. Historical temperatures are not future projections, and neither automatically becomes an asset loss estimate.

`manifest.json` records SHA-256 checksums for the bundled dataset files at build time.
